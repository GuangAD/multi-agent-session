# 0006 - agent 接入采用仓内静态插件与显式注册

日期:2026-11-22 | 状态:已采纳

## 背景

新增 agent 需要改至少四处核心代码:shared 类型里封闭的 AgentId 联合、渲染层硬编码的图标与品牌色映射、注册表的手工 import 登记、住在导入域里的会话扫描器(由此产生 AGENTS.md 记录的「领域横向依赖双向例外」)。接入成本随 agent 数量线性上升,核心被 agent 清单反复穿透。

## 决策

1. agent 接入采用**仓内静态插件**:每个 agent 一个自包含插件包(声明数据、状态规则、扫描器、fixture、品牌图标与配色同住),在插件清单登记一行。
2. **显式注册**,不做目录扫描自动发现。
3. 插件能力面收敛为:必选五声明(身份、启动命令、状态识别规则、品牌图标、品牌色)+ 可选两行为(会话扫描、续接参数);状态规则保持声明式数据。
4. agent id 开放为字符串;渲染层由 agents:list 载荷驱动(图标 SVG 字符串 + 品牌色),未知 agent 兜底渲染。
5. 运行时外部插件(npm 包/独立目录动态加载)不做;未来需要时仅替换注册方式,插件包结构不变。

## 为什么不用 运行时外部插件

- 不可信代码进主进程需要沙箱与插件 API 版本化,复杂度翻数倍
- asar 打包要为外部插件目录开洞,分发形态复杂
- 当前没有真实需求:五个 agent 全部在仓内、同仓演进

## 为什么不用 目录扫描自动发现

- 打包器下动态 import 要绕路(electron-vite 静态分析)
- 插件失去编译期类型检查
- 收益仅是省一行登记,代价不成比例

## 后果

- 接入成本 = 一个自包含目录 + 一行登记;核心文件不再被 agent 清单穿透
- 「导入框架 ←→ 定义」双向依赖例外消灭:扫描器随插件走,导入域只留通用编排与扫描 SDK(单向:插件 → 框架)
- AgentId 失去编译期穷举检查,换取插件免改核心类型;渲染层兜底渲染补位
- 渲染层品牌图标从硬编码组件表改为载荷驱动(SVG 字符串内联渲染)
