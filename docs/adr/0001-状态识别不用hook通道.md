# 0001 - 状态识别不用 hook 通道

日期:2026-11-20 | 状态:已采纳 | **2026-11-24 标注:决策依据的事实基础已过时(codex/antigravity 推出官方 hooks、四家支持项目级注入、各家 hook 失败语义均 fail-open),被 ADR-0007(0007-状态识别走hook通道取代读屏.md)取代;本文保留历史,对账详见 0007 与 docs/agent-hooks-capability-survey.md**

## 背景

应用需要显示每个会话的运行状态(干活/等输入/空闲/退出)。参考实现 Orca 采用「屏幕规则 + hook 上报」双通道:hook 侧子系统约 179 个非测试文件、2.3 万行,需要向用户全局配置(如 `~/.kimi-code/config.toml`、`~/.pi` 插件文件)注入钩子,并由本地服务接收上报。

## 决策

自研「三源」流式识别引擎:标题事件(xterm onTitleChange)+ 屏幕快照(常驻实例缓冲区节流读取)+ 字节流环形缓冲,外加进程退出事件;不实现 hook 通道,列为将来可选升级。

## 为什么不用 hook 通道

- 2.3 万行的子系统相对本应用规模过大,移植与维护不成比例
- 注入配置写入用户全局目录,影响应用外的全部同类会话
- 多会话并发下「随会话清理」语义不成立(两个会话同时退出,谁清配置)
- claude/pi/codex/antigravity 四家有 Orca 验证过的旁观信号,hook 的净收益只剩 kimi/antigravity 两家

## 后果

- kimi/antigravity 的等输入精度可能不足:已配降级预案(最坏只做「有输出=干活、退出=退出」),M3 采样后按实际精度决定是否重提 hook
- 换来:不写任何用户全局配置,应用外零影响,实现量从万行级降到百行级
- codex 的屏幕重绘型信号在字节流里不可靠,识别以屏幕快照为主——已列入覆盖标准
