# Agent TUI 运行机制讲解:从概念到本项目实现

> 2026-11-23 | 性质:科普向讲解文档(非任务文档,不属于四层文档体系)
> 回答的问题:agent CLI 的 TUI 界面(pi/claude 等)在本项目里是通过什么技术手段跑起来的。
> 面向读者:对终端/PTY/TUI 不熟悉的开发者。

一句话全景:**这个应用 = 一台 Windows 假终端(ConPTY)+ 一个网页里的终端电视机(xterm.js)+ 中间的字节搬运通道(Electron IPC)+ 三个偷看状态的探头**。agent 始终以为自己在跟一台真终端对话,应用只是把这场对话原样搬进了自己的窗口。

---

## 第 0 层:程序和终端是怎么对话的(一切的地基)

先建立一个核心认知:**pi、claude 这类程序从来不会直接「画屏幕」。它们只会往一个叫 stdout 的输出口写字节,从一个叫 stdin 的输入口读字节**。这些字节变成什么,取决于对面接的是什么东西。

**情况 A:stdout 接的是文件。**比如 `dir > list.txt`,字节全进了文件,屏幕上什么都没有。

**情况 B:stdout 接的是终端窗口。**(你在 Windows Terminal 里敲 `pi` 就是这种。)终端窗口不是普通文本框,它是一台「字符电视机」:

- 屏幕 = 一张网格,比如 165 列 × 40 行,每个格子放一个字符
- 程序写的字节里,普通字符(如 `π`)的含义是「在光标位置放这个字符,光标右移一格」
- 另一种特殊字节叫**转义序列**(以 ESC 字节 `\x1b` 开头),它们不是字符,是**给终端的指令**:

| 程序发出 | 终端执行 |
|---|---|
| `\x1b[2J` | 清屏 |
| `\x1b[10;5H` | 光标移到第 10 行第 5 列 |
| `\x1b[31m` | 之后写的字用红色 |
| `\x1b[?1049h` | 换一块新黑板(「交替屏」,全屏 TUI 用的),退出时 `?1049l` 换回来 |
| `\x1b[?25l` | 藏起光标(TUI 自己管光标) |
| `\x1b[?1000h` | 开启鼠标上报(之后鼠标点击/滚轮会变成字节发回给程序) |

**TUI 的全部秘密就在这**:pi 的输入框边框,是它写了一串 `╭─┬╮` 字符;颜色是它先发颜色指令再写字;spinner 转圈,是它每约 100ms 擦掉重写同一个格子。claude、pi 里看到的一切,都是「移动光标 + 写字符」两件事的组合——程序自己一格一格地画。

**键盘方向**:你按键,终端把按键编码成字节发给程序的 stdin。普通字符就是字符本身(`h` 就是 `h`);功能键有约定编码,比如 ↑ 是三个字节 `\x1b[A`,Enter 是 `\r`。程序读到字节就知道你按了什么。

所以「跑一个 TUI」= 两台机器在互相发字节:程序发画画指令,终端发键盘编码。**终端和程序是两个独立进程,靠字节流对话,谁也不认识谁。**

## 第 1 层:为什么要有个「假终端」(ConPTY)

Electron 桌面应用想在自己窗口里跑 pi。能不能在主进程里直接启动 pi、读它的 stdout?

**不能,因为 stdout 接管道(pipe)时 pi 会「变脸」。**程序启动时会检测「我的 stdout 接的是终端吗」(有专门的系统 API)。接管道 = 不是终端 → pi 认为对面不能画画 → 退化成纯文本输出:没有颜色、没有边框、没有实时刷新,甚至拒绝交互。TUI 程序必须看到一台「终端」才肯演。

解决方案就是**伪终端(PTY)**:操作系统提供一个「假终端」对象。程序接到假终端上,一查——「对面是台 165 列的终端,支持真彩色」,于是正常开演;假终端的另一头接的是**我们的程序**,我们就能收到它的全部字节、替它转发。

Windows 上这套东西叫 **ConPTY**(微软 2018 年起提供的伪控制台 API)。它是个**中间人**:

```
pi 的字节流   ──→ ConPTY(自己还抄一份屏幕内容的账本)──→ 我们的程序
我们的字节流 ──→ ConPTY ──→ pi 的 stdin
```

ConPTY 不是纯管道,它会**翻译和重排**——这是很多 Windows 特有行为(整屏重绘、resize 通知丢失、鼠标序列被吞)的根源,下文场景 3 会展开。

## 第 2 层:本项目里的角色对照

| 角色 | 是什么 | 代码落点 |
|---|---|---|
| pi / claude | TUI 程序,只管发指令、收按键 | 外部 CLI,不属于本仓 |
| ConPTY | 假终端 + 中间人,Windows 系统组件 | 操作系统提供,node-pty 调用 |
| node-pty | Node.js 里操作 ConPTY 的封装库:spawn、收发字节、改尺寸 | `src/main/pty-registry.ts` |
| PowerShell | 常驻 shell,坐镇 PTY 里;pi 是它启动的子进程 | 同上(ADR-0004) |
| xterm.js | **终端电视机的 JS 实现**:解析转义序列、维护网格、画像素、捕键盘 | `src/renderer/src/components/terminal/use-terminal.ts` |
| IPC(`pty:data` / `pty:write`) | 主进程和渲染层之间的字节搬运工 | `src/main/ipc/pty.ts` + `src/renderer/src/ipc/bridge.ts` |

**为什么中间要隔一道 IPC?**Electron 是两个世界:渲染层是 Chrome 网页(xterm.js 必须活在网页里才能显示),主进程是 Node 世界(只有这里能用 node-pty 这种原生模块)。渲染层被禁止直接 import Node 模块(工程红线,见 AGENTS.md),所以字节必须经 IPC 搬一次。这就是代码里到处是 `bridge.pty.write` / `pty:data` 的由来。

**为什么 PTY 里坐的是 PowerShell 而不是直接坐 pi?**这是 ADR-0004 的产品决策:pi 退出(`/quit`)后用户要回到提示符继续敲命令、还能再进 pi。所以应用永远只 spawn 一次 PowerShell(常驻),pi 是「坐上来」的客人,由 PowerShell 的启动参数带起来:`powershell -NoLogo -NoExit -Command "chcp 65001 …; & 'pi' …"`。代价:pi 是 shell 的子进程,杀标签页时要杀整棵进程树(`killProcessTree`)。

## 场景 1:新建会话(从 0 到看到 pi 界面)

1. 用户点侧栏会话 → 渲染层先建好一台「终端电视机」:xterm 实例 + 空网格,并用 fit 算出真实尺寸(比如 165×40)。**先量好尺寸再要进程**,pi 一出生就知道自己是 165 列宽(Windows 下 pi 收不到运行期 resize,启动宽度是它的终身宽度)
2. 渲染层发 `pty:spawn`(带 sessionId、尺寸、项目目录)→ 主进程 `pty-registry.ts` 的 `spawn()`:
   - `resolveCommandPath('pi')` 查 PATH 确认已安装(只探测,不起进程)
   - node-pty 调 ConPTY:**spawn powershell.exe**,初始尺寸 165×40,cwd = 项目目录,环境变量注入 `TERM=xterm-256color` 等(pi 靠它决定开不开真彩/鼠标);`useConptyDll: true` 用微软 Terminal 1.23 的 conpty.dll(老版 ConPTY 会吞鼠标模式序列)
3. pi 进程在 PowerShell 里启动。它检测「stdout 接的是什么」→ ConPTY 答「一台 165×40 的终端」→ pi 决定进入全屏模式
4. pi 开始往 stdout 写第一批字节(示意):
   ```
   \x1b[?1049h        ← 换新黑板(交替屏)
   \x1b[2J            ← 擦干净
   \x1b[1;1H          ← 光标回原点
   \x1b[?25l          ← 藏起光标
   ╭──────────╮       ← 开始画边框(夹着颜色指令)
   ```
5. 字节先到 ConPTY:它自己也存一份屏幕内容(账本),把指令规范化后往下游发
6. node-pty 的 `onData` 回调触发(pty-registry.ts:340)→ 主进程把这包字节打上 sessionId,经 IPC 事件 `pty:data` 推给渲染层
7. 渲染层的「数据泵」(use-terminal.ts:185,全应用唯一)按 sessionId 找到对应 xterm 实例,调用 `xterm.write(字节)`
8. xterm 内部:**解析器**逐字节解析(普通字符还是指令),据此修改自己的网格数据——每个格子记着「字符 + 颜色 + 样式」
9. **webgl 渲染器**把网格画成像素(`─╭╮` 这类制表符走矢量自绘,见 docs/issues/2026-11-23-box-drawing-seams.md)
10. 用户看到 pi 的输入框

第 4-9 步在 pi 运行期间**永远在重复**:pi 每重绘一帧就发一批字节,这条链跑一遍。链路上没人积压——主进程只转发,渲染层直灌 xterm。

## 场景 2:用户敲了一个字母 `h`(输入链)

1. 键盘事件落在 xterm 的网页 DOM 上
2. xterm 把按键编码成字节:`'h'` 一个字符(若是 ↑ 则是 `\x1b[A` 三个字节,Enter 是 `\r`)
3. xterm 触发 `onData('h')`(use-terminal.ts:244)→ 渲染层发 `pty:write`
4. 主进程 `ptyRegistry.write(id, 'h')` → node-pty 写进 ConPTY
5. ConPTY 转交 pi 的 stdin
6. pi 收到 `'h'`,往自己的输入框画这个字:**又往 stdout 写一批「移光标 + 写 h」的字节** → 走场景 1 的第 5-10 步 → 用户看到输入框里出现 h

所以每敲一个键,字节走一圈「渲染层 → 主进程 → ConPTY → pi → ConPTY → 主进程 → 渲染层」。**终端里每个字的变化都是 pi 重新画出来的,不是应用画的。**应用只是忠实搬运。

## 场景 3:拖大窗口(resize 链——Bug 1/3 所在通道)

1. 窗口变大 → 浏览器通知渲染层:容器尺寸变了(ResizeObserver)
2. fit 重新算网格:能放 180 列了 → `terminal.resize(180, 40)` → xterm 网格变大
3. xterm 触发 `onResize`(use-terminal.ts:247)→ 渲染层发 `pty:resize(180, 40)`
4. 主进程 → node-pty → **ConPTY 改尺寸**。ConPTY 手里的「屏幕账本」是按旧宽度记的,宽度一变,所有行的折行位置全变 → 它把账本按新宽度**重新排一遍,然后整屏重发一遍字节**(resize 后终端「闪一下重画」的原因)
5. 理想情况下 pi 也应收到「宽度变了」的通知自己重画。**但 Windows 上不可靠**:pi 实测收不到,一辈子按启动宽度画,画面更新全靠 ConPTY 重发

**Bug 1/3 坏在哪一环**(详见 docs/issues/2026-11-22-session-row-spinner-and-state.md):切走标签时,本该只影响「电视机」的 fit 把**假终端 ConPTY 也一起改成了 2×1**(第 3-4 步被误触发)——等于告诉系统「这台终端只有 2 个格子宽」。ConPTY 按 2 列重排账本、pi 画面被搅碎,切回来又要重排回来整屏重发——这就是「切回黑屏等一会」。Bug 本质:**只是想藏起一台电视机,却顺手把电视台也改了。**

## 旁路:状态识别是怎么「偷看」的

上面三条链,应用全程只是搬运工,**从不理解内容**。侧栏 spinner 怎么知道 pi 在忙?靠三个探头偷看:

1. **标题**:程序可以改窗口标题(一条转义指令),xterm 的 `onTitleChange` 上报——claude 干活时标题里带转圈字符
2. **屏幕快照**:渲染层每 250ms 把 xterm 网格上的**纯文字**抄一份(`translateToString`),上行主进程——pi 干活时屏幕上有点阵动画帧
3. **字节环**:主进程转发 `pty:data` 时顺手抄一份进 64KB 环形缓冲

主进程状态引擎(`src/main/agent-state/state-parser.ts`)拿三样做**关键字匹配**(不解析语义,就是 substring):「屏幕上有 working 地标 + 最近 2 秒有动静 = working」,经 300ms 去抖广播给侧栏。它是猜状态的旁观者,会被骗——Bug 1(塌缩快照骗了它)和 Bug 2(用户打字回显骗了它)都是旁观者被骗,终端本体没坏。

## 收拢

- agent 以为自己在跟真终端对话,对面实际是 ConPTY + xterm.js
- 应用没有实现任何 agent 逻辑,做的是「一台忠实的终端 + 一个会话档案柜」
- 三条链:输出链(字节→像素)、输入链(按键→字节)、尺寸链(fit→resize→ConPTY 重排);状态识别是三条链之外的旁观者
- Windows 特有行为的源头大多在 ConPTY:整屏重绘、resize 通知丢失、鼠标序列透传问题(`useConptyDll`)
